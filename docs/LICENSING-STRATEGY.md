# 许可策略提案（Licensing Strategy Proposal）

> **状态：提案，未生效。** 本文件不改变仓库任何现有许可证，当前生效的许可归属仍以
> [README.md](../README.md) 的双许可表、[LICENSE](../LICENSE) 全文与各文件 SPDX 头为准。
> 本文只陈述判断与代价，
> 决策权在 maintainer。本文不构成法律意见；涉及具体合同、管辖与税务时需执业律师确认。

**TL;DR** — Licence should follow the revenue model, not code importance. The current
"core AGPL / tooling Apache" split defends well but blocks the paying customer segment
(commercial Android apps). Recommended direction: relax the core, keep the strict licence
for what can be sold as a service, and lock copyright consolidation now while it is free.

---

## 1. 结论摘要

1. 许可应当跟随**收费形态**，而不是跟随**代码重要性**。
2. 当前「核心防护层 AGPL-3.0-only + 外围工具 Apache-2.0」在防守上成立，在采用与变现上自伤。
3. AGPL §13 只对「通过网络与该程序交互」生效；`guard-mcp` 走 stdio 本地进程，**不触发**，
   所以它现在挂 AGPL 的实际约束力接近于零。
4. 现阶段最优不是「设计好许可去防人」，而是「降低门槛换采用」，同时用版权集中保留将来切换的权利。
5. 现在唯一必须做、且成本近乎为零的事是**版权集中**（DCO + 保留商业授权权）。
   `0.1.0-alpha5` 尚未发布，这是最后的低成本窗口。

## 2. 现状诊断

| 模块 | 当前许可 | 判定依据 | 副作用 |
|---|---|---|---|
| `guard-core` / `guard-ksp` / `guard-ui` | AGPL-3.0-only | 核心防护层，整体分发受 AGPL 约束 | 商业闭源 App 集成即传染整个 App → 挡住最大的付费客群 |
| `guard-mcp` | AGPL-3.0-only | 编译 `guard-core` 源进同一产物 | 本地 stdio 不触发 §13 → 实际约束力≈0；真正的风险在「被别人做成托管网关」 |
| `sample/` | AGPL-3.0-only | 链接核心 | 合理，示例应随核心 |
| `guard-audit` / `guard-cli` | Apache-2.0 | 不链接防护层 | 合理 |

问题不在「分得不对」，而在**分的方向**：最需要被广泛采用的一层被设成了最严格的那张证。

## 3. 三条判定原则

- **P1 传染半径最小化**：库用宽松许可，服务用严格许可。收钱发生在服务上，严格许可就该卡在服务上。
- **P2 许可与收费点对齐**：如果收费点是「托管网关 / 审计后端 / 企业策略中心」，许可就该约束这些形态，
  而不是约束所有下游集成的静态链接。
- **P3 可逆性优先（关键）**：从宽松改严格，需要**全部版权人**同意；从严格改宽松，只需版权人一人同意。
  因此在早期选「宽松 + 版权集中」，等于把两种未来都保留下来；先设严格看似安全，
  代价是永久损失一段采用量——而采用量改不回来。

## 4. 三个可选方案

| 方案 | 采用门槛 | 防白嫖 | 商业授权可行性 | 迁移成本 |
|---|---|---|---|---|
| **A 维持现状**（核心 AGPL / 工具 Apache） | 高（商业 App 基本不敢用） | 强 | 低（没人会为被挡在门外的东西付钱） | 0 |
| **B 核心放宽 + 服务侧严格**（推荐方向） | 低 | 中强（卡住托管形态） | 高（有人用，才有人问授权与支持） | 中（改动清单见 §7） |
| **C 全面 Apache + 纯服务收费** | 最低 | 弱（云厂商可直接托管） | 中（靠服务差异化，不靠许可） | 中 |

B 与 C 的差别只有一个：别人把你的东西做成**对外收费的托管服务**时，你能不能要求他开源或买授权。
B 保留了这个抓手，代价是核心那层不再有许可层面的商业保护。

## 5. 推荐路线（分阶段，不合并执行）

**阶段 0 — 现在（1 天内可完成，成本≈0）**
- 引入 DCO sign-off 或轻量 CLA，完成版权归集；在 `GOVERNANCE.md` 保留「商标与商业授权权归 maintainer」条款。
- 把 README 中「闭源集成需商业许可」一类表述，改写为「如需其他许可安排，请联系 maintainer」。
  在没有 CLA 与合同模板之前，前一种写法只是「禁止」，不构成「可购买」。
- ⚠️ 本阶段不改变任何现有许可。

**阶段 1 — 出现外部采用（第三方 fork、issue、集成案例）之后**
- 核心层转 Apache-2.0（或维持宽松双选），把严格许可留给 §6 描述的服务形态。
- 已发布的版本许可不可撤回，历史说明保留在 CHANGELOG。

**阶段 2 — 有企业明确询价之后**
- 企业功能/托管服务单独立仓，用严格许可（AGPL-3.0-only 或 BSL，注意 BSL 不是 OSI 认可许可）；
- 此时才需要合同模板、报价与支持 SLA；此前一律不承诺商业授权。

**明确不做**
- 不现在拆仓（维护成本大于收益）；
- 不在没有版权集中的情况下承诺 dual licensing；
- 不同一仓库混用 AGPL 与 BSL 而不加说明（会让 `GPL-3.0` 工具链的识别结果自相矛盾）；
- 不把赞助当作收入路径（0 用户阶段是信号，不是收入）。

## 6. 为什么现状的约束力比看上去弱

- `guard-mcp` 通过 stdin/stdout 与宿主 Agent 通信，是本机进程，不存在「通过网络与该程序交互」，
  不落入 AGPL §13 的触发条件。
- 真正的暴露面：有人把 `guard-mcp` 或 `guard-core` 包装成**对外提供服务的托管网关**。此时 §13 生效，
  他必须提供对应源码——这正是 B 方案要保留的抓手，也是「商业授权」唯一卖得动的场景。
- 组织内网自用通常不构成「向公众提供」，但各地认定不同，需具体评估。
